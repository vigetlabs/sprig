# Seed-planting memory & performance: the version-3 stack

This documents a 7 part series of code changes that resolve excessive memory usage in Sprig,
along with a detailed analysis of the changes and their impact. Several identified bugs are
fixed at appropriate points along the way. They are presented as a stack for ease of review
and understanding; they are _not_ intended to be partially implemented.

Each part is its own commit; each commit's message states why that specific change
reduces memory and the measured before/after for that change alone, using the scripts in
this directory.

## The dataset

Five models, seeded together in one `sprig()` call, always declared and offered in
dependency-last order (the hardest case, not an opt-in flag):

| Model        | Fields (type)                                                                                                                                                | Dependency                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Customer`   | `name` (string), `contact_email` (string), `signed_up_on` (date), `active` (boolean), `annual_revenue` (decimal), `employee_count` (integer), `notes` (text) | none (independent)                                                                                                                                 |
| `Tag`        | `name` (string), `category` (string)                                                                                                                         | none (independent); a small, fixed ~20-row vocabulary that doesn't scale with dataset size                                                         |
| `Project`    | `title`, `status`, `budget`, `starts_on`, `billable`, `priority`, `customer_id`                                                                              | **optionally** a `Customer` (~70% of rows)                                                                                                         |
| `Task`       | `title`, `description`, `due_on`, `estimated_hours`, `completed`, `assignee_name`, `project_id`                                                              | **always** a `Project`                                                                                                                             |
| `ProjectTag` | `project_id`, `tag_id`, `added_on` (date)                                                                                                                    | **always** a `Project` _and_ a `Tag` -- the many-to-many edge between them, and the only model here that depends on two independent things at once |

Generated by `generate_customers.rb` / `generate_tags.rb` / `generate_projects.rb` /
`generate_tasks.rb` / `generate_project_tags.rb` (Faker, fixed random seeds for
reproducibility), or all five at once via `generate_dataset.rb <dir> <n>`. Three
volumes: N = 1,000 (small) / 10,000 (medium) / 100,000 (large), scaling
customers/projects/tasks 1:1:1 and project_tags at ~2.5x projects (so N=1,000 seeds
5,520 total rows; N=100,000 seeds 550,020).

**Directives are always offered dependency-last**: `ProjectTag, Task, Project, Tag,
Customer`. Every `ProjectTag` is offered before any `Project` or `Tag` exists; every
`Task` before any `Project`; most `Project`s (the ~70% with a `customer_id`) before any
`Customer`. This is the only ordering this suite measures -- the old stack's separate
well-ordered/`REVERSE=1` toggle is gone; adversarial ordering is realistic (a Rails app's
seed files are rarely hand-sorted by dependency), and it's the scenario that actually
distinguishes a scheduler that holds the whole dataset from one that doesn't.

This dataset's dependency graph is still shallow (`ProjectTag`/`Task` → `Project` →
`Customer` is at most 2 hops), so, unlike a long self-referencing chain, it never risks a
`TSort` stack overflow regardless of N -- that failure mode is a property of chain
_length_, not graph width, and isn't what this dataset is built to exercise. Its role
here is field/type richness, realistic optional and many-to-many relationships, and
adversarial ordering under a fixed, moderate graph depth.

## What each part does

Each part also has its own writeup ([part-1](part-1.md), [part-2](part-2.md),
[part-3](part-3.md), [part-4](part-4.md), [part-5](part-5.md), [part-6](part-6.md),
[part-7](part-7.md)) with the full mechanism, empirical evidence at every tier, and
anything else from that stage's own commit message -- the summary below is the short
version.

- **part-1**: benchmark harness only, no `lib/` changes -- the baseline every later part
  is measured against; it contains no functional changes to the code of Sprig.
- **part-2**: introduces `Sprig::Seed::Descriptor`, a lightweight placeholder (raw row +
  class + options) pushed into the hopper instead of a fully-built `Entry`. An `Entry` --
  with every field wrapped, type-cast, and dirty-tracked -- is only built at the instant a
  record is actually planted.
- **part-3**: makes `Dependency#id` a deterministic string instead of a cached
  `SecureRandom.uuid`, and deletes the global `DependencyCollection` registry that used to
  keep every `Dependency` object ever created alive for the whole run.
- **part-4**: replaces the whole-graph `DependencySorter` (build the entire dependency
  graph, topologically sort it, _then_ plant) with an incremental scheduler: a record
  plants the instant everything it depends on has already been planted; anything else is
  held, indexed by what it's still waiting on, and woken (iteratively, not recursively) the
  moment that dependency lands. **NOTE: This is a bug fix, not just a memory
  optimization** -- the old whole-graph `TSort`-based sort recurses per node, and a long
  self-referencing chain declared newest-first overflows Ruby's stack
  (`SystemStackError`) at roughly 11,000 records deep.
- **part-5**: `SprigRecordStore` stops holding the live saved record forever, keyed by
  class + `sprig_id` -- it holds just the record's real primary key. `#get` returns a
  `Sprig::SprigRecordStore::LazyRecord` that answers `.id` directly with zero database
  access, and only falls through to a real `klass.find(id)` if something beyond the id is
  actually asked of it.
- **part-6**: `Parser::Yml`/`Json` stream rows directly off the source `IO` via a
  `Psych::Parser`/`Oj::ScHandler` event handler instead of `YAML.load`/`JSON.load`-ing the
  entire file into memory as a monolithic nested structure before a single row is processed.
- **part-7**: adds opt-in `Sprig.configuration.spill_seed_rows_to_disk`. A descriptor
  that's actually determined to be waiting (not every descriptor -- only ones genuinely
  blocked) spills its raw row data to a small disk-backed log and reads it back once,
  right before planting. Off by default - only helps for highly-referential, badly sorted seeds.

## Methodology

[`run_benchmark.rb`](run_benchmark.rb) plants the dataset through the real, public Sprig
pipeline (`Sprig::Helpers#sprig`, real `ActiveRecord` models, real saves) against a real,
separate PostgreSQL server -- not in-process SQLite. SQLite's own storage (B-tree pages,
buffers) runs inside the same OS process being measured and would be counted alongside
Sprig's own memory.

Requires Docker, assumed already running:

```bash
# Start (once per benchmarking session)
docker run --name sprig-benchmark-postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=sprig_benchmark \
  -p 5433:5432 \
  -d postgres:15.2-alpine

until docker exec sprig-benchmark-postgres pg_isready -U postgres; do sleep 1; done

# Tear down when done
docker stop sprig-benchmark-postgres && docker rm sprig-benchmark-postgres
```

Port 5433 (not Postgres's default 5432) avoids colliding with any Postgres already
running locally. Connection is configurable via `SPRIG_BENCHMARK_PG_{HOST,PORT,USER,
PASSWORD,DATABASE}`, defaulting to match the command above. `run_benchmark.rb` truncates
its tables at the start of each run, since a real Postgres server persists data between
invocations (unlike SQLite `":memory:"`, which resets automatically per process).

To reproduce, from a checkout of each branch being compared:

```bash
ruby benchmark/generate_dataset.rb /tmp/bench_1k 1000
ruby benchmark/generate_dataset.rb /tmp/bench_10k 10000
/usr/bin/time -l bundle exec ruby benchmark/run_benchmark.rb /tmp/bench_1k    # macOS
/usr/bin/time -l bundle exec ruby benchmark/run_benchmark.rb /tmp/bench_10k
```

Each run is one isolated OS process (`/usr/bin/time -l` on macOS / `-v` on Linux, for
wall-clock time and peak RSS measured by the kernel, not by the Ruby process itself).
Every branch is checked out into its own `git worktree`; nothing is looped inside a
single Ruby process, since Ruby's allocator reuses warmed-up memory arenas across
repeated similar allocations in the same process and would make later runs in a
sequence look artificially cheap. `SPILL=1` enables
`Sprig.configuration.spill_seed_rows_to_disk` once that option exists (part-7
onward); it's never passed on earlier branches, which abort cleanly if forced.

### Instrumented runs: memory/object-count traces and storage-space-over-time

Alongside the plain `/usr/bin/time -l` peak-RSS numbers below, every branch/tier was also
run under [`benchmark/instrumented_run.rb`](instrumented_run.rb) -- a diagnostic harness,
committed for reproducibility but explicitly **not** part of the library or
`run_benchmark.rb`'s pipeline (see the header comment in that file) -- which polls RSS and
`GC.stat` counters at a fixed interval throughout the run, computes the memory-time
integral (storage-space-over-time, in MB-seconds -- the area under the RSS-vs-time curve,
via the trapezoidal rule over the actual sampled timestamps) once the run finishes, and
takes a one-time post-run `ObjectSpace` breakdown of the specific retained structures
under investigation (`SprigRecordStore`'s held records, the old whole-graph sorted array,
the scheduler's waiting/pending set).
[`benchmark/analyze_traces.rb`](analyze_traces.rb) -- also committed, also diagnostic-only
-- turns those raw traces into the numbers quoted throughout this doc.

Two things worth knowing before reading those traces yourself:

- **Per-tick sampling is limited to O(1) counters (RSS, `GC.stat`).**
  `ObjectSpace.each_object`/`reachable_objects_from` are full-heap walks whose cost scales
  with total live object count; run repeatedly during a run, they compete for the GVL with
  the actual planting work badly enough to turn an ~11-minute run into 40+ minutes without
  finishing (discovered directly, not anticipated). The `ObjectSpace`-based breakdown is
  computed exactly once, after the run, in `*_final_breakdown.txt` -- which means it's a
  single snapshot, not a trajectory; per-item structural costs quoted below come from that
  one point in time for each run, not from watching a value rise and fall during planting.
- **A live-object count at one instant doesn't distinguish real retention from ordinary GC
  sweep lag.** A snapshot can show, say, several thousand live `Descriptor`s right after a
  run finishes and look like a leak until you force a `GC.start` immediately before
  re-checking -- confirmed directly in an earlier pass of this investigation, where doing
  exactly that made every count involved drop to exactly zero. The per-branch
  `entry_count`/`descriptor_count`/`dependency_count` numbers below are read with that
  caveat in mind: real, structural differences (e.g. "part-3 always ends at exactly zero
  live `Dependency` objects, every run") are trustworthy; small numeric wobbles between
  otherwise-similar branches are not asserted as meaningful.

| ---------------------------------------------- | ------------------------------: | -------------------------------: | ------------------------------------: |

| part-2 (Descriptor)                            |                 93.3 MB (-9.0%) |                370.4 MB (-10.1%) |                   2,168.3 MB (-23.0%) |
| part-3 (dependency slimming)                   |                 92.7 MB (-9.6%) |                346.0 MB (-16.0%) |                   1,914.3 MB (-32.1%) |
| part-4 (incremental scheduler)                 |                 93.6 MB (-8.7%) |                 392.4 MB (-4.7%) |                   2,020.9 MB (-28.3%) |
| part-5 (`SprigRecordStore` lazy re-fetch)      |                79.8 MB (-22.2%) |            228.2 MB (**-44.6%**) |               1,232.0 MB (**-56.3%**) |
| part-6 (streaming parsers)                     |                75.3 MB (-26.6%) |            115.2 MB (**-72.0%**) |                 509.0 MB (**-81.9%**) |

All percentages are cumulative, against the part-1 baseline at that tier.

**Storage-space-over-time** (memory-time integral -- see above; MB-seconds at small/medium
tier, GB-seconds at large tier):

| Branch                                         |                                         Small (1K) |                          Medium (10K) |                             Large (100K) |
| ---------------------------------------------- | -------------------------------------------------: | ------------------------------------: | ---------------------------------------: |
| part-1 (harness baseline)                      |                                        186.2 MB\*s |                         7,712.5 MB\*s |                              890.3 GB\*s |
| part-2 (Descriptor)                            |                                171.5 MB\*s (-7.9%) |                6,809.0 MB\*s (-11.7%) |                      875.8 GB\*s (-1.6%) |
| part-3 (dependency slimming)                   |                                169.9 MB\*s (-8.8%) |                6,475.4 MB\*s (-16.0%) |                     797.6 GB\*s (-10.4%) |

| part-5 (`SprigRecordStore` lazy re-fetch)      |                               156.8 MB\*s (-15.8%) |            4,787.5 MB\*s (**-37.9%**) |                 299.8 GB\*s (**-66.3%**) |
| part-6 (streaming parsers)                     |                               148.2 MB\*s (-20.4%) |            2,652.0 MB\*s (**-65.6%**) |                 135.3 GB\*s (**-84.8%**) |
| part-7, `SPILL` off (this stack's default)     |                               148.6 MB\*s (-20.2%) |                2,670.2 MB\*s (-65.4%) |                     129.2 GB\*s (-85.5%) |
| part-7, `SPILL=1` (opt-in, explicitly enabled) | 179.7 MB\*s (**+20.9%** vs. `SPILL` off, see note) | 2,546.2 MB\*s (-4.6% vs. `SPILL` off) | 100.1 GB\*s (**-22.5%** vs. `SPILL` off) |

`SPILL=1`'s small-tier MB-seconds figure is a genuinely different verdict from its own
peak-RSS number in the table above, not a typo: peak RSS drops (75.3 -> 72.9 MB) but the
memory-time integral _rises_ (148.6 -> 179.7 MB*s), because `SPILL=1`'s small-tier wall
time is itself longer (2.02s -> 2.53s, +25%) -- holding a somewhat lower amount of memory
for a meaningfully longer time nets out to *more\* total storage-space-over-time, not less.
At medium tier both metrics agree it's a win, because the added wall time is proportionally
much smaller there (23.4s -> 24.8s, +6%). This is exactly the distinction peak RSS alone
can't make, and part of why this metric is worth tracking alongside it.
